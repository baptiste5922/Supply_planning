# Supply Planning & Data Analytics Portfolio

A learning-first portfolio that simulates a supply planning analytics stack end to end — from
synthetic source data to a reconciled SQL/BI layer — for a fictional outdoor-products company,
**Alpiflow**. Built to prepare for roles at the intersection of supply planning, data analysis, BI
and digital transformation (the target role brief is in `docs/PROJECT_BRIEF.md`).

> **Disclaimer.** Alpiflow does not exist. Every dataset in this repository is synthetic,
> generated by a deterministic script (`scripts/generate_sample_data.py`). This project has no
> access to, and makes no claim about, any real company's systems or data.

## The three projects

| # | Project | Question it answers | Status |
|---|---|---|---|
| 1 | **Supply Planning Control Tower** | Where are demand, supply, capacity and inventory out of balance, and by when? | Data model, ingestion, KPIs and exceptions done ([Phase 1](#phase-1--supply-planning-control-tower) below). BI report blocked — see [Limitations](#known-limitations). |
| 2 | **Demand Forecasting & Inventory Optimisation** | Would a forecast beat a simple baseline, and how would that change a replenishment decision? | Not started. |
| 3 | **ERP-to-APS Digital Transformation Simulator** | Can a business process be turned into traceable requirements, tests and a transparent planning simulation? | Not started. |

Full task-by-task status lives in `docs/ROADMAP.md`.

## Approach

- **Learning-first, one vertical slice at a time.** Each roadmap task moves one slice
  (source → ingestion → PostgreSQL → calculation) forward rather than scaffolding the whole system
  up front. See `CLAUDE.md` for the working contract this was built under.
- **Three data layers, one source of truth per field.** `raw` keeps exactly what the source sent
  (including its errors); `clean` keeps only what passed validation; `analytics` is the layer BI
  tools read. See `docs/ARCHITECTURE.md`.
- **Nothing is guessed.** Every business number (lead times, safety stock, capacity shares,
  service targets) is a labelled, configurable assumption (`ASM-xx` in `docs/BUSINESS_RULES.md`),
  never a hard-coded default. Every invalid or missing data point is reported, never silently
  dropped or defaulted.
- **Every non-trivial calculation has a hand-checked example** before it's trusted against the
  full dataset — see the 3-week worked example in `tests/test_planning.py`.

## Phase 1 — Supply Planning Control Tower

### Data model

Three PostgreSQL schemas, same seven tables in each (`dim_product`, `dim_calendar`,
`dim_supplier`, `fct_demand_actual`, `fct_inventory_snapshot`, `fct_purchase_order_line`,
`fct_capacity`), plus `fct_projected_inventory` in `analytics` only:

```
CSV (synthetic source) --extract--> raw --validate--> clean --copy--> analytics --> SQL / BI
```

Grain, keys, units and missing-data rules for every field are in `docs/DATA_DICTIONARY.md`.
Why three schemas instead of one, and why `clean`/`analytics` are identical in v1, is explained in
`docs/ARCHITECTURE.md` §2.

### KPIs implemented

| KPI | Definition | Where |
|---|---|---|
| Weeks of cover | On-hand ÷ average forward weekly demand, capped at 13 weeks, never infinite | `src/supply_planning/planning/coverage.py` |
| Projected shortage | `max(0, safety_stock − projected_inventory)` via the week-by-week inventory recurrence | `src/supply_planning/planning/projected_inventory.py` |
| Capacity utilisation | Planned load ÷ available capacity, **not** capped at 100% so overload stays visible | `sql/006_planning_outputs.sql` (`v_capacity_utilisation`) |
| Supplier OTIF | Lines received exactly on the promised date ÷ lines due, 0-day tolerance | `sql/006_planning_outputs.sql` (`v_supplier_otif`) |

Exact formulas, caveats and the mandatory hand-calculated example are in `docs/BUSINESS_RULES.md`
§4 and `tests/test_planning.py`.

### Results on the sample dataset

Running the pipeline below against the committed 120-product sample (`data/sample/`) produces:

- 4 data-quality issues caught by ingestion, matching `data/sample/README.md`'s documented edge
  cases exactly (one missing SKU-week, one negative available stock, one rejected purchase-order
  line, one capacity overload).
- Capacity utilisation of **122.3%** for the `FOOT` family in the week of 2026-06-15 — a real,
  disclosed overload, not a bug.
- Overall supplier OTIF of **~33%**, consistent with the generator's documented delivery-outcome
  mix.
- 117 of 120 SKUs showing a projected shortage within 13 weeks — a known property of this sample
  data (demand and inventory are generated independently, not as one consistent simulation; see
  [Limitations](#known-limitations)), not a defect in the calculation.

All four numbers are reproduced by the manual verification steps in [Getting started](#getting-started).

## Getting started

Tested on macOS with Python 3.14.3 and PostgreSQL installed via Homebrew.

```bash
# 1. Isolated virtual environment (never committed)
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

# 2. Dependencies
python -m pip install --upgrade pip
python -m pip install -r requirements.txt

# 3. Local configuration (never commit .env)
cp .env.example .env
#    then edit .env with your local PostgreSQL values

# 4. Create a least-privilege role and a dev database, then the schema
#    Run as a PostgreSQL superuser once; PGUSER/PGDATABASE must match your .env.
#    If your machine already runs PostgreSQL on the default port for other
#    work, point PGHOST/PGPORT in .env at a separate instance or port first
#    (this project's own dev instance runs on 5433 for exactly that reason).
createuser --login --pwprompt supply_planning_app
createdb --owner=supply_planning_app supply_planning_lab
for f in sql/*.sql; do psql -d supply_planning_lab -U supply_planning_app -f "$f"; done

# 5. Automated tests — no database needed for this step
python -m pytest

# 6. (Optional) Regenerate the synthetic sample dataset — deterministic,
#    re-running it reproduces data/sample/*.csv byte-for-byte
PYTHONPATH=src python scripts/generate_sample_data.py --preset sample

# 7. Run ingestion: data/sample/ -> raw -> clean -> analytics,
#    logging row counts and every data-quality issue found
PYTHONPATH=src python scripts/run_ingestion.py

# 8. Run the planning KPIs: the projected-inventory recurrence for every
#    product, written to analytics.fct_projected_inventory
PYTHONPATH=src python scripts/run_planning.py
```

Expected result at step 5: `100 passed`. Steps 7 and 8 are the only steps that write to
PostgreSQL; step 7 should report exactly 4 issues (see `data/sample/README.md` for exact keys),
and step 8 should flag most SKUs as `infeasible_replenishment` — expected, per the limitation
above, not an error.

## Known limitations

- **No Power BI report yet.** The semantic model, DAX measures and page specification are fully
  written and SQL-validated (`docs/POWER_BI_REPORT.md`), but the `.pbix` itself does not exist:
  Power BI Desktop requires Windows (unavailable here), and the Power BI Service alternative
  requires a work/school Microsoft account, which this project doesn't have. Both blockers are
  environmental, not design gaps — see `docs/POWER_BI_REPORT.md` §4.1.
- **117 of 120 sample SKUs show a projected shortage.** This sample's demand and inventory are
  generated independently of each other, not as one consistent supply/demand simulation — a
  deliberate scope cut for a small fixture, documented in `data/sample/README.md`.
- **No currency or unit cost anywhere in the data model.** Excess stock can be shown in pieces,
  never in money — any "where do we tie up cash" question can only be answered in units.
- **The 95%/98% service-level target (`ASM-08`) is a registered assumption, never wired into a
  calculation.** Weeks-of-cover numbers exist; a concrete target to compare them against does not.
- **Replenishment suggestions are computed but not persisted** to any table — `replenishment.py`
  returns a suggested order quantity/date, but P1.5's acceptance criteria only required the logic
  and its tests, not a stored output.
- **Phases 2 and 3 (forecasting, ERP integration) are not started.**
