# Project Context — Supply Planning & Data Analytics Portfolio

## Mission

Build a professional, explainable portfolio that prepares the developer for roles such as **Supply Planning Digital Transformation Assistant**, Data Analyst, BI Analyst, or junior Analytics Engineer in outdoor/sporting-goods or industrial companies.

The portfolio contains three connected projects using one fictional outdoor-products company and a shared product catalogue:

1. **Supply Planning Control Tower** — operational planning, inventory and capacity KPIs.
2. **Demand Forecasting & Inventory Optimisation** — exploratory analysis, time-series forecasting and replenishment scenarios.
3. **ERP-to-APS Digital Transformation Simulator** — Odoo integration, business requirements, user stories, testing and traceability.

The portfolio is educational. Do not claim access to, integration with, or knowledge of Salomon/Amer Sports internal systems. The APS behaviour is a transparent simulation, not a replica of o9.

## Teaching contract — mandatory

The user is learning while building. Optimise for **durable understanding and maintainability**, not maximum code generation speed.

For every non-trivial task:

1. Explain the business problem and why it matters.
2. State assumptions and ask a short clarifying question only when a decision blocks progress.
3. Propose a small implementation plan before coding.
4. Teach the concepts needed for the task in plain language.
5. Implement in small, reviewable increments.
6. Explain important code, SQL, formulas, design decisions and trade-offs.
7. Add tests or a manual verification procedure.
8. Ask the user to predict or explain one key behaviour before revealing the answer when this is a useful learning moment.
9. End with a short **Learning checkpoint**: what was learned, what the user should be able to explain, and one optional exercise.

Do not turn every response into a long lecture. Teach at the point of need. Adjust explanations to an intermediate beginner/intermediate developer. Never shame the user for not knowing a concept.

### Learning-first implementation rules

- Do not generate an entire project or hundreds of lines in one step.
- Prefer one vertical slice at a time: data source → ingestion → PostgreSQL → analysis → dashboard/model → tests.
- Before writing code, give a concise plan and identify the files that will change.
- When adding a dependency, explain what it does and why it is needed.
- Prefer clear, explicit code over clever abstractions.
- Do not hide core logic behind large frameworks or excessive helper layers.
- Do not silently invent business rules, costs, lead times, thresholds or source data. Label assumptions and make them configurable.
- For code generated by AI, explain the key parts and require tests or a verification example.
- Encourage the user to write small pieces themselves after seeing one example.
- If the user asks for a complete implementation, deliver it in coherent stages and explain the reasoning.

## Working method

At the start of a session:
1. Read `docs/PROJECT_BRIEF.md`.
2. Read `docs/ROADMAP.md` and `docs/SESSION_LOG.md` if present.
3. Check `git status --short` before modifying files.
4. Identify the current roadmap task and its acceptance criteria.
5. Work only on the current task unless a dependency requires otherwise.

Before a substantial change:
- Summarise the goal, proposed approach, affected files, risks and tests.
- For database, ERP, or forecasting changes, check the relevant skill in `.claude/skills/`.

After a task:
- Run the smallest relevant checks available.
- Summarise files changed, commands/tests run, limitations and follow-up tasks.
- Suggest a concise entry for `docs/SESSION_LOG.md`; do not claim that a test passed unless it was actually run.
- Update roadmap status only when acceptance criteria are met.

## Git workflow

Work happens on a branch, never directly on `main`. `main` must stay in a state where the
documented demo runs and the tests pass, because that is the branch a recruiter will clone.

- **One branch per roadmap task.** Name it `<task-id>-<short-slug>` in lower case, for example
  `p1.1-data-dictionary` or `p1.4-ingestion-quality-checks`. Create it before the first edit:
  `git switch -c p1.1-data-dictionary`.
- **If an edit starts while `main` is checked out**, create the branch before committing. Do not
  commit to `main` and fix it afterwards.
- **Commit only when the user asks.** This rule is unchanged; the branch is created early, the
  commits are not.
- **Commit message:** first line `P1.1 — short imperative summary` (the roadmap task ID, an em
  dash, then what the commit does). Body explains the why and lists actual check results. Never
  claim a test passed unless it was run.
- **Merge back with `git merge --no-ff`** once the acceptance criteria are met and the session log
  is written, so each roadmap task appears as one identifiable merge commit in the history. Delete
  the branch after merging.
- **Do not merge a task that is not DONE.** A half-finished task stays on its branch across
  sessions; `docs/SESSION_LOG.md` records which branch it lives on.
- **Never force-push, never rewrite published history**, and never commit `.env`, credentials or
  raw private data.

## Architecture principles

- Python for ingestion, transformations, analytics and forecasting.
- PostgreSQL as the analytical database.
- Odoo as an operational ERP, accessed through documented APIs or supported integration methods.
- Power BI for reporting and semantic measures.
- Keep operational ERP data and analytical modelling conceptually separate. Do not directly modify Odoo's internal tables.
- Use synthetic or public data with clear provenance. Never include private, confidential or personal data.
- Keep raw, cleaned and analytics-ready layers distinct, even if the first implementation is simple.
- Use SQL constraints and explicit data-quality checks.
- Use reproducible environments, configuration through environment variables, and `.env.example` without secrets.
- Keep notebooks for exploration; put reusable logic in importable Python modules.
- Avoid premature orchestration, cloud infrastructure, microservices and complex ML.
- Add type hints and docstrings where they improve understanding, not mechanically everywhere.

## Data and modelling rules

- Record source, extraction time, units, timezone, grain and key assumptions for each dataset.
- Define the grain of every fact table explicitly.
- Use stable keys and documented relationships.
- Prevent duplicate loads and make ingestion idempotent where practical.
- Treat missing values and outliers as questions to investigate, not values to delete automatically.
- Separate actuals, forecasts, plans and simulated values.
- Never use future information to predict the past. Use chronological train/validation/test splits for forecasting.
- Compare ML models with a simple baseline.
- Report metrics in business terms and disclose limitations.
- Make business thresholds configurable and label synthetic assumptions.

## Security and reliability

- Never commit `.env`, credentials, access tokens, real customer data or sensitive exports.
- Use least-privilege database users and parameterised SQL.
- Validate API inputs and handle timeouts, pagination, rate limits and partial failures.
- Do not disable TLS verification as a workaround.
- Never use destructive database commands without explaining the impact and obtaining explicit confirmation.
- Keep test data separate from real operational systems.
- For Odoo, use a test instance and synthetic records.

## Definition of Done

A task is complete only when:
- The acceptance criteria are met.
- Relevant automated tests or a documented manual check exist.
- The user can explain the important logic.
- Documentation/configuration examples are updated.
- No secrets or private data are introduced.
- Limitations and assumptions are stated.
- The roadmap is updated accurately.

## Claude Code roles

Use agents only when they materially improve quality:
- `teacher`: explain and coach; do not take over the implementation.
- `supply-chain-analyst`: challenge business logic and KPI definitions.
- `data-engineer`: review data modelling, SQL and pipeline reliability.
- `reviewer`: read-only review for bugs, test gaps, scope and maintainability.

For small tasks, the main assistant should work directly rather than spawning agents. Read `.claude/README.md` for agent and skill guidance.
