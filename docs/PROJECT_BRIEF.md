# Project Brief

## Target role

Prepare for roles at the intersection of supply planning, data analysis, BI and digital transformation, such as the Supply Planning Digital Transformation Assistant internship described by Salomon/Amer Sports.

## Portfolio story

Build one fictional outdoor-products company and three connected projects. Use one shared product catalogue, calendar and set of synthetic sales/supply records so that the work feels like a coherent system.

### Project 1 — Supply Planning Control Tower

**Question:** Can planners see where demand, supply, capacity and inventory are out of balance?

Outputs:
- PostgreSQL analytical model.
- Reproducible Python ingestion and validation.
- Supply planning calculations and exception list.
- Power BI dashboard with inventory, capacity and delivery KPIs.
- Synthetic test scenarios.

### Project 2 — Demand Forecasting & Inventory Optimisation

**Question:** Can forecasts improve planning decisions compared with a simple baseline?

Outputs:
- Time-series EDA.
- Baseline and at least one statistical forecasting model.
- Chronological or rolling-origin validation.
- MAE/RMSE and appropriate metric caveats.
- Replenishment scenarios based on forecast, lead time and stock position.
- Power BI comparison of actuals, forecasts and errors.

### Project 3 — ERP-to-APS Digital Transformation Simulator

**Question:** Can business requirements be translated into a tested, traceable planning workflow?

Outputs:
- Odoo test-instance integration through a supported API/export.
- Process map (current and proposed process).
- Requirements catalogue and user stories.
- Acceptance criteria and test cases.
- Requirements-to-design-to-test traceability matrix.
- Data-quality and planning-exception report.
- Clearly labelled APS simulation.

## Scope boundaries

- Do not implement a production-grade APS optimiser.
- Do not use confidential company data.
- Do not claim an actual o9, SAP or Salomon integration.
- Do not build a complex cloud deployment before the local version works.
- Do not add deep learning unless a clear business need and enough data justify it.
- Prefer a finished, tested, explainable vertical slice over a large incomplete system.

## User's learning goals

The developer should progressively learn to:
- Explore and validate business data.
- Model relational data and write understandable SQL.
- Build reliable Python ingestion and transformation.
- Design meaningful Power BI models and measures.
- Evaluate time-series forecasts correctly.
- Understand ERP data and supported integrations.
- Document processes, user stories, acceptance criteria and tests.
- Explain design choices without depending on AI.

## Definition of portfolio success

A recruiter can run the documented demo, inspect the data model and dashboard, understand the business question, and ask the developer to change a rule or query live. The developer can explain the relevant logic and limitations.
